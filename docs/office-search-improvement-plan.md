## 0. 결정

**지금은 청킹·임베딩을 넣지 않는다. 먼저 검색을 잴 수 있게 만들고(S-01·S-02), 지금 규모에서 검색 누락을
구조적으로 없애는 우회 경로(S-03)만 넣는다.** 나머지는 숫자가 나온 뒤에 한다.

코드만 보면 "어휘 매칭뿐이다", "본문을 앞 3,000자에서 자른다"가 가장 큰 약점으로 보인다. 운영 데이터는 그렇게 말하지 않는다.

## 1. 실측 (2026-11-17, 운영 `ovlo` DB — 집계만 조회, 질문 본문은 읽지 않았다)

| 항목 | 값 |
|---|---|
| 승인 공지 | 4건, 평균 248자, 최대 318자 (보관 18건) |
| 3,000자 넘는 공지 | 0건 |
| 질문 | 34건, 전부 계정 1개, 2026-11-12 ~ 11-16 |
| 결과 | ANSWERED 21 · OUT_OF_SCOPE 7 · NO_GROUNDS 5 · ESCALATED 1 |
| NO_GROUNDS 5건 | 후보 0건 2 · 후보는 있었는데 탈락 3 (사유는 DB 에 없다) |
| DB 이미지 | `postgres:16-alpine` (16.13) — `pg_trgm` 1.6 사용 가능, pgvector 없음 |

읽는 법:

- "3,000자 잘림"과 "임베딩 부재"는 지금 데이터에서 한 번도 발생하지 않는 문제다.
- ADR-0006 6항의 벡터 전환 조건(자료 수천 건, 또는 검색 누락 20% 초과)은 충족되지 않았다. 후자는 **잴 수단이 없어** 판단 자체가 안 된다.
- 질문 34건이 전부 계정 1개라 이 분포는 실사용이 아니다. 비율을 근거로 쓰지 않는다.

## 2. 확인된 구멍

1. **검색이 한 번도 평가된 적이 없다.** `OfficeAiLiveEvaluationTest` 는 `NoticeSearchPort` 를 mock 으로 바꿔
   항상 정답 공지를 돌려준다. 지금 평가가 보증하는 것은 "정답 공지가 후보에 있을 때"의 가드·답변·검증뿐이다.
2. **탈락 사유가 남지 않는다.** 후보 없음, 모델의 NO_GROUNDS, 모델 거부, 인용 없음, 범위 밖 인용, 근거 검증 DENY,
   저장 직전 근거 변경이 모두 같은 `NO_GROUNDS` 로 저장되고 사유는 로그에만 있다. 위 표의 "후보는 있었는데 탈락 3건"이
   프롬프트 문제인지 자료 문제인지 지금은 알 수 없다.
3. **후보가 0건이 되는 경로가 불필요하게 넓다.** 공지가 4건(약 1KB)인데도 질문과 토큰이 하나도 안 겹치면 후보 0건으로
   끝난다. 표현만 다른 질문("생활관" vs "기숙사")이 여기에 걸린다.

코드에서 읽은 약점(실측으로 확인되지는 않은 것):

- PG 어댑터의 FTS 는 `simple` 구성이라 한국어 조사가 붙은 어절을 못 맞추고, CJK 는 전체 공지를 읽어 Java 에서 bigram 점수를 낸다.
- ADR-0006 1항의 분류(`category`) 가중치와 `tsvector` 생성 컬럼 + GIN 은 구현돼 있지 않다(ADR 2026-11-13 보완에 명시).
- 후속 질문은 직전 질문 2개를 이어 붙여 검색한다.
- 공지 본문은 20,000자까지 등록되지만 후보 본문은 앞 3,000자만 쓴다(`NoticeAnswerLimits.MAX_BODY_CHARS`).

티켓 하나가 PR 하나다. 끝난 뒤에도 앱이 뜨고 테스트가 통과한다. 순서대로 한다.

| S-06 | **긴 공지 경고** — 3,000자를 넘는 공지를 등록·수정할 때 담당자 화면에 "챗봇은 앞 3,000자만 읽습니다" 경고와 메트릭 | 경고는 저장을 막지 않는다. 지금은 0건이라 청킹 대신 감지만 한다 |

## 4. 조건이 찰 때까지 하지 않는 것

| 항목 | 착수 조건 | 미리 알아둘 것 |
|---|---|---|
| 문단 청킹 | S-06 경고가 실제로 발생하거나, 승인 공지 총량이 S-03 상한을 넘을 때 | 인용 단위가 공지에서 문단으로 바뀐다. `NoticeCitation`, 근거 스냅샷 비교(`NoticeAnswerFinalizer.sameEvidence`), 학생 화면의 출처 표시까지 손봐야 한다 |
| pgvector 하이브리드 검색 | ADR-0006 6항 그대로 — 자료 수천 건, 또는 S-01 의 `NO_CANDIDATES` 중 정답 공지가 있었던 비율이 담당자 표본 검토에서 20% 초과 | 운영 이미지가 alpine(musl)이다. pgvector 공식 이미지(Debian, glibc)로 바꾸면 콜레이션이 달라져 텍스트 인덱스를 다시 만들어야 하고, 교체 전 전체 백업과 복구 리허설이 필요하다. 임베딩 공급자도 따로 정해야 한다 — Anthropic 은 임베딩 API 가 없고, gpunode 로컬 모델은 꺼지는 장비라 운영에 쓸 수 없다. 공지 수정마다 재임베딩이 생긴다 |
| 질문을 한국어로 번역해 원문도 검색 | S-02 에서 "번역은 있는데 번역 표현으로 못 찾는" 유형이 실제로 나올 때 | ADR-0006 에 실험 항목으로 적혀 있으나 구현되지 않았다. LLM 호출 1회 추가 |

## 5. 판단이 필요한 점

- **S-03 은 설계 원칙을 조금 바꾼다.** 지금은 "검색된 것만 모델에 넣는다"인데 소규모에서는 "전부 넣는다"가 된다.
  재현율은 100% 가 되지만 답변·검증 호출의 입력 토큰이 늘고(지금 규모에서는 약 1KB), 저장 직전 "후보 중 하나라도 바뀌면 보류"
  정책(ADR-0006 2026-11-15)이 후보가 많아진 만큼 더 자주 걸릴 수 있다. 근거 검증은 실제 인용된 자료만 받으므로 영향이 없다.
- **검색보다 큰 병목은 자료와 사용자다.** 공지 4건에 사용자 1명이면 어떤 검색 개선도 체감되지 않는다.
  S-01·S-02 는 실사용이 생기기 전에 해 둘 가치가 있지만, S-04 이후는 실제 질문이 쌓인 뒤에 하는 편이 맞다.
- **권장 범위: S-01 ~ S-03 까지만 지금.** 골든셋 러너와 사유 코드는 다른 프로젝트의 챗봇에도 그대로 쓸 수 있다.

## 6. 실측 기록

### S-02 첫 기준 — 2026-11-17

`origin/main@f12ecb4`에서 합성 공지 28건·질문 70개(ko/en/ja/zh/vi/de/fr 각 10개)를 측정했다.
운영 자료나 질문은 사용하지 않았고 LLM 호출은 없다. 두 어댑터는 같은 fixture와 정답 ID를 사용한다.
PostgreSQL은 Testcontainers의 `postgres:16-alpine`과 실제 Flyway·저장 어댑터를 사용한다.

| 어댑터 | recall@8 (정답 검색 / 질문) | 후보 0건 | 후보가 있지만 정답 누락 |
|---|---|---|---|
| KeywordNoticeSearchAdapter | **0.800000 (56/70)** | 6 | 8 |
| PostgresFtsNoticeSearchAdapter | **0.800000 (56/70)** | 6 | 8 |

| 유형 | 질문 수 | Keyword 누락 | PostgreSQL 누락 |
|---|---:|---:|---:|
| 직접 어휘 일치 | 24 | 0 | 0 |
| 조사 붙은 한국어 | 4 | 0 | 0 |
| 바꿔 말한 표현 | 14 | 14 | 14 |
| 후속 질문 (저장된 앞 질문 결합) | 14 | 0 | 0 |
| 3,000자 뒤의 검색 단서 | 7 | 0 | 0 |
| 주제가 겹치는 공지 | 7 | 0 | 0 |

- 검색 단계만 평가한다. 긴 공지의 정답 후보를 찾았어도 답변 단계의 앞 3,000자 제한을 통과했다는 뜻은 아니다.
- 각 질문은 정답 공지 1건을 지정했다. recall@8은 질문별 `검색된 정답 수 / 전체 정답 수`의 평균이며,
  보고서에 모든 정답의 순위와 첫 정답 순위를 기록한다. 순위 `0`은 상위 8건에서 누락이다.
- fixture는 짧은 주제별 공지와 다국어 표현을 통제한 합성 세트다. 이 80%를 운영 검색 성능이나
  ADR-0006의 운영 누락률로 해석하지 않는다. 실제 질문의 다양성과 자연스러운 공지 본문을 대변하지 않는다.
- 누락은 기숙사 환불·주소 변경을 동의어로 물은 경우다. 조사와 후속 질문은 이 세트에서 누락이 없었다.
  따라서 S-05의 LLM 검색어 재작성 착수 근거는 아직 없다. S-04는 §5의 실사용 조건에 따라 보류한다.
- `src/test/resources/retrieval/office-search-baseline.json`에 **어댑터별 0.8 하한과 기존 성공 56개 케이스**를
  고정한다. 전체 점수가 같더라도 기존 성공 질문의 정답이 빠지면 실패한다. fixture SHA-256도 확인한다.
  기준을 갱신할 때는 보고서를 검토하고 이 표와 baseline을 함께 명시적으로 변경한다.

재현 명령:

```bash
./gradlew test --tests '*KeywordNoticeRetrievalTest'
./gradlew integrationTest --tests '*PostgresNoticeRetrievalIntegrationTest'
```

출력: `build/reports/retrieval/{keyword,postgres}.{json,csv}`. JSON에 질문·실제 검색어·후보 ID·정답별 순위·
유형별/언어별 집계를, CSV에 질문별 점수를 남긴다. PR CI도 두 러너를 실행하고 보고서를 artifact로 보존한다.


### S-04~S-06 착수 판단 — 2026-11-17

S-02 결과와 S-03·개인정보/번역 복구 PR #96을 포함한 `origin/main@51274d3`를 대조했다.
§1의 운영 실측값은 그대로 사용했으며 재조회하지 않았다. 후속 작업 진행 요청에 따라,
§5의 권장 범위에서 예방적 진단인 **S-06만 먼저 진행**한다.

| 티켓 | 판단 | 근거 |
|---|---|---|
| S-04 | 보류 | 누락 14건은 동의어 표현이다. 조사·직접 일치·주제 중첩은 모두 통과했다. 조사 처리나 제목/분류 가중치를 바꿀 실측 근거가 없고, 합성 세트의 동의어에 맞추는 변경은 §5의 실사용 조건을 충족하지 않는다. |
| S-05 | 보류 | 두 어댑터 모두 후속 질문 14/14 통과. 검색어 재작성이나 LLM 호출 추가의 이득이 확인되지 않았다. |
| S-06 | 진행 | 긴 본문이 등록 가능하고 답변 입력에서 3,000자로 잘리는 전제가 그대로다. 검색의 긴 본문 7/7 성공은 답변 완전성을 뜻하지 않는다. 지금 0건이라는 §1 수치를 바꾸지 않고 향후 발생을 감지한다. |

S-06 동작 및 계측:

- 담당자 공지 등록·편집 화면에서 본문이 3,000자를 넘으면 경고한다. 처음 불러온 긴 공지에도 표시하고,
  다시 짧게 고치면 사라진다. 기존 20,000자 입력 상한과 저장·승인 절차는 유지한다.
- 길이는 기존 저장/답변 코드와 같은 UTF-16 단위다. 저장 시 제거하는 앞뒤 `U+0000..U+0020`을 제외한다.
  답변 잘림과 서버 감지는 `NoticeAnswerLimits.MAX_BODY_CHARS`를 공유하고 프론트 회귀 검사에서 같은 값을 확인한다.
- `ovlo_office_notice_long_body_total{action="REGISTER"|"UPDATE"}`는 긴 **원문**을 저장한 커밋 횟수다.
  중복 없는 공지 수나 현재 긴 공지 재고가 아니며, 같은 긴 공지를 다시 저장하면 증가한다.
  짧은 본문·실패·롤백은 집계하지 않는다. 두 시계열은 앱 시작 시 0으로 등록하고 프로세스 재시작 시 초기화된다.
  본문·공지 ID·회원 ID·학교 ID를 메트릭에 넣지 않는다. 번역 결과 길이는 이 경고의 범위 밖이다.
