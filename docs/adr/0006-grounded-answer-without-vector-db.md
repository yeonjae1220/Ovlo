# ADR-0006: 파일럿의 근거 검색은 벡터 DB 없이 PostgreSQL FTS + LLM 인용 검증으로 한다

- 상태: Proposed
- 날짜: 2026-10-30
- 결정자: Backend
- 관련 설계: [국제처 파일럿 제품 설계](../intl-office-pilot-design.md) §5.2, §8
- 관련 Pitfall: GLOBAL-PIT-064(게이트 화이트리스트 맹점), GLOBAL-PIT-108(실패를 빈 값으로 치환 금지)

## 맥락

학생 질문에 "국제처 승인 자료만 근거로" 답하려면 (1) 후보 자료를 고르고 (2) LLM이 후보 안에서만 답하게 하고 (3) 그 답이 실제로
후보를 인용했는지 확인해야 한다. 일반적인 방법은 임베딩 + 벡터 DB(pgvector 등)다.

파일럿 조건: Office 1곳, 승인 자료 수십~수백 건, 언어 7개. 운영 DB는 k3s의 PostgreSQL 16이며 확장(pgvector) 추가는 이미지 교체와
백업·복구 절차 확인이 필요하다. 임베딩 모델 선택·갱신(자료 수정 때마다 재임베딩)도 운영 부담이다.

## 결정

1. **1단계는 pgvector를 도입하지 않는다.** 후보 검색은 PostgreSQL 전문 검색(`tsvector` 생성 컬럼 + GIN)으로 한다.
   원문(`simple` 구성)과 학생 언어 번역을 함께 색인하고, 분류(`category`)가 질문에서 추정되면 가중치를 준다. 상위 K(기본 8)를 후보로 쓴다.
2. 후보는 반드시 `Notice.isGroundingEligible(today, lang)`를 통과한 것만이다(APPROVED, 유효기간 안, 번역 stale 아님). 이 필터는
   SQL이 아니라 **도메인 메서드**가 최종 판정한다. SQL은 1차 걸러내기만 한다.
3. LLM에는 후보 본문을 ID와 함께 넣고, "후보에 있는 내용만, 문장마다 `[ID]` 인용, 답할 수 없으면 정확히 `NO_GROUNDS`"를 지시한다.
4. **후처리 검증**이 최종 게이트다: 인용 ID 집합이 후보 집합의 부분집합이 아니거나 인용이 0개면 `NO_GROUNDS`로 강등하고 경고 로그를 남긴다.
   답변에 URL이 있으면 후보 Notice의 `sourceUrl`만 허용한다. 검증 실패를 "답변 없음"이 아니라 **강등 + 기록**으로 다루는 이유는
   LLM이 지시를 어긴 빈도를 봐야 프롬프트를 고칠 수 있기 때문이다.
5. 모든 Inquiry에 후보 ID·인용 ID·지연·모델 ID를 저장한다. 이것이 FTS의 재현율이 부족한지(후보에 정답 공지가 없어서 NO_GROUNDS가
   난 비율) 판단할 근거다.
6. **벡터 검색으로 바꾸는 조건**: Office 수가 늘어 자료가 수천 건이 되거나, NO_GROUNDS 중 "정답 공지가 있었는데 후보에 못 들어간" 비율이
   담당자 표본 검토에서 20%를 넘으면 pgvector(또는 외부 벡터 저장소)를 `NoticeSearchPort` 구현 교체로 도입한다. 포트는 처음부터 분리한다.

## 결과

- 장점: 운영 DB 변경이 Flyway 테이블·인덱스뿐이다. 자료 수정이 즉시 반영된다(재임베딩 없음). 비용은 LLM 호출뿐이다.
- 단점: 동의어·다른 표현의 질문은 FTS가 놓칠 수 있다. 특히 한국어 원문과 외국어 질문 사이는 번역 색인에 의존한다.
  이를 보완하려고 질문을 한국어로 한 번 번역해 원문 색인도 함께 검색하는 2단계 검색을 S3에서 실험한다(LLM 호출 1회 추가).
- S3 구현에서 정한 것(2026-10-31):
  - 질의는 AND 가 아니라 **OR**(`to_tsquery('simple', 'a | b | c')`)이다. 'simple' 구성은 불용어를 빼지 않아 "when does the …" 같은
    질문이 AND 로는 아무 문서도 못 찾는다. 짧은 기능어 몇 개만 제외하고, 매칭 여부는 `@@` 로 강제한 뒤 `ts_rank` 합으로 정렬한다
    (`ts_rank` 만으로는 매칭되지 않은 문서도 0 보다 큰 점수를 받는다).
  - 한국어·일본어·중국어 질문은 띄어쓰기 단위 FTS 가 약하다(조사가 붙은 "신청은"은 "신청"과 다른 토큰). 그래서 PG 어댑터가
    글자 2개 묶음(bigram) 점수(`KeywordNoticeSearchAdapter`)로 후보를 보강한다. 이 bigram 방식이 기본 구현이기도 하다
    (`ovlo.search.provider=keyword`, 로컬·테스트).
  - 두 구현은 `NoticeSearchPort` 뒤에 있고, 최종 근거 자격은 언제나 `Notice.isGroundingEligible` 이 판정한다.
- 테스트: FTS 어댑터는 Testcontainers PostgreSQL로 "만료 공지 제외", "다른 Office 공지 제외", "번역 stale 제외"를 고정한다.
  후처리 검증은 순수 단위 테스트(후보 밖 인용 → 강등, 인용 0 → NO_GROUNDS, 외부 URL 제거).

## 2026-11-13 보완

[ADR-0007](0007-office-ai-abuse-controls.md)은 질문 범위 검사, 인용 검사 뒤 독립 근거 검증,
Sonnet 답변 모델 분리와 호출 전 원자적 예산 예약을 추가한다. 이제 후보가 없더라도 범위 검사 호출은 발생할 수 있다.
현재 PostgreSQL 어댑터는 쿼리 시점 `to_tsvector`를 사용한다. 위 생성 컬럼/GIN과 질문 번역 검색은 구현된 기능으로 간주하지 않는다.


## 2026-11-15: 답변 확정은 근거 스냅샷을 비교한다

공지의 JPA `rowVersion`은 다른 언어 번역 저장·검수 표시·만료 알림 기록에도 증가한다. 따라서 LLM 호출 전후의
행 수정 번호가 다르다는 이유만으로 `NO_GROUNDS`로 낮추지 않는다. 학교 잠금을 얻은 최종 저장 트랜잭션에서
다음 항목을 호출 전 스냅샷과 비교하고 현재 근거 자격도 다시 검사한다.

- 원문 내용 버전, 제목·본문·분류·언어·출처 URL·첨부·학기·유효기간
- 출처 메타데이터, 출처 검토 정보, 승인자·승인 시각
- 번역 언어로 질문했다면 그 언어의 번역 제목·본문·원문 버전
- 현재 승인·유효기간·출처 검토 상태, 공식 URL 허용 범위 및 기반 자료의 유효성

다른 언어 번역과 시각/검수 표시만 바뀐 동일 내용의 번역은 답변을 유지한다. 사용한 번역의 내용 변경이나
원문 변경·철회·재승인은 계속 보류한다. 쓰기 경합 방지용 `rowVersion` 자체와 낙관적 락은 유지한다.
새 DB 컬럼이나 마이그레이션은 필요하지 않다. 사용하지 않은 다른 후보가 변경될 때 모든 후보를 다시 검사하는
기존의 보수적인 정책은 유지한다.

`NoticeGovernanceIntegrationTest`가 PostgreSQL의 실제 커밋을 사이에 둔 회귀 사례를 검증한다.
유료 동시 호출 검증은 `OVLO_LIVE_LLM=1 ./gradlew integrationTest --tests '*NoticeGovernanceIntegrationTest.realLlmAnswerOverlapsTranslationCommit'`로 실행한다.
`ANTHROPIC_API_KEY`는 환경변수로만 전달하며, 한국어·영어 답변(Sonnet)과 프랑스어 번역(Opus)을 동시에 호출한다.
제공자 호출 구간의 실제 중첩, 번역 저장에 따른 revision 증가, 답변 유지와 인용 저장을 확인한다.
합성 데이터 결과는 `build/reports/live-answer-concurrency/{ko,en}.json`에 저장한다.


## 2026-11-17 보완 — 소규모 자료의 검색 우회 (S-03)

그 학교에서 요청 언어의 `isGroundingEligible`과 `governance.eligible`을 모두 통과한 공지 전체가
`candidateLimit`(기본 8건)과 30,000 UTF-8 바이트 이내이면 어휘 점수와 무관하게 모두 후보로 사용한다.
바이트는 모델에 사용할 언어의 **전체 제목 + 본문 + 공개 출처 URL + 적용 대상·캠퍼스**를 합산하며, 기존 제목 200자·본문 3,000자 절단 전 값이다.
상한은 포함한다. 건수나 바이트 중 하나라도 넘으면 기존 키워드/FTS 검색으로 돌아간다.
후보의 순서는 ID 내림차순으로 고정한다. 비공개 출처·내부 참조 정보의 노출 정책은 바꾸지 않는다.

`SmallNoticeCorpus.MAX_CONTEXT_BYTES`를 후보 예산과 답변 문맥의 바이트 제한이 함께 사용한다.
두 검색 어댑터 모두 같은 자격·예산 판정을 거친다. 학교 범위를 재확인하며, 영어 질문에서 영어 번역이 없는
공지처럼 근거 자격이 없는 자료는 건수·용량에도 포함하지 않는다. 자격 있는 공지가 없는 경우 빈 후보를 반환한다.

범위 밖 질문은 기존 앞단 가드가 검색 호출 전에 차단한다. 답변의 인용 검사·독립 근거 검증과 저장 직전
모든 후보의 근거 변경 검사는 유지한다. 작은 자료 집합에서는 입력 토큰 및 변경 검사 대상이 늘어난다.
수집 쿼리는 기존 `findActiveForStudent`를 사용하므로 학교의 활성 자료 전체를 읽는다. 자료가 커지는 단계의
SQL·페이지 최적화는 별도 검색 성능 작업으로 다룬다. 검색 대상 전체를 후보에 넣어도 긴 본문 절단 문제를 해결하지 않는다.

검증: 두 어댑터의 8/9건·30,000/30,001바이트·UTF-8·요청 언어·학교 범위·검토 보류/만료/출처 자격
경계 테스트, 실제 PostgreSQL의 작은 자료 우회 및 초과 시 기존 검색 복귀, 기존 질문 가드 회귀 테스트.

## 2026-11-17 후속: 적용 범위의 명시적 전달

`NoticeSource.audience/campus`는 본문과 별도로 저장되는 공개 적용 조건이다. 학생 공지 목록·상세 DTO와 답변 후보에 두 필드만 허용 목록으로 추가한다. 내부 `reference`, 갱신 담당자와 기반 자료 ID는 학생 응답이나 모델 입력에 넣지 않는다. 답변·검증 모델은 동일한 구조화 필드를 받으며 조건의 확대·누락을 거절하고, 필드 안의 지시문은 신뢰하지 않는 데이터로 처리한다. 입력 예산은 유지하고 적용 조건 대신 본문을 줄인다. 조건을 온전히 담을 수 없는 후보는 제외한다.

학생 상세 화면에는 승인된 원문 언어의 적용 범위를 별도 표시한다. 기존 본문 번역이 이 필드도 번역한 것처럼 표시하지 않는다. 답변 모델은 해당 조건의 의미를 학생의 요청 언어로 전달한다. 별도 유료 호출·DB 마이그레이션은 추가하지 않는다. 출처 정보 변경 시 기존 버전 증가·재승인·근거 무효화 정책을 유지한다.
